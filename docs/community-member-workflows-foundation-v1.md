# Community member workflows: current contract

A community has one ordered workflow of stages. A member's position belongs to the active community membership. If there is no stored stage row, the first stage is resolved from the membership's activation time; reading this default does not write state.

A stage has a name, optional agent instructions, optional goal, a `Require human approval` setting, and up to twelve trigger-to-action rules. The supported triggers are first join, member post or reply, submitted form, time in stage, and verified completion of the immediately preceding action. The supported actions are create a private service channel, request a form, and ask the community agent. A trigger starts an action; it is not evidence that the action finished.

## Completion and movement

The completion reader verifies an outcome for every configured action in the current membership activation and stage visit. A private channel must be available, a requested form must have a valid submitted record, and an agent response must have been delivered. Dispatch, queued work, failed work, old visits, changed rules, and truncated scans do not count. A stage with no actions is never complete for automatic movement.

After the last verified action, a stage without a goal can advance automatically unless human approval is required. A stage with a written goal starts a bounded, private assessment when approval is not required. Only an achieved verdict with current evidence may advance it. Not-yet, insufficient evidence, failure, or changed authority leaves the member in place. The assessment does not post a member message or run tools.

For stages requiring human approval, the owner or an admin approves the current visit. All configured actions must be verified first. A written goal starts the same bounded agent assessment after action completion, but its verdict is advisory and never advances the member. A failed, unavailable, or negative assessment does not block human approval. A zero-action manual stage can be approved deliberately without running an assessment. Approval records the actor and goal snapshot; it is separate from Force move and does not assert goal achievement.

Force move is an owner/admin override that may bypass unfinished actions or an unmet goal. It records the actor, rejects stale or repeated confirmations, closes pending stage forms, and does not imply goal achievement.

## Retired action model

`Move member` conditions and user-configured `Evaluate goal` actions are retired. The editor and definition schema contain only the three supported actions; cached clients that submit retired actions fail validation. A September 23, 2026 census found no retired workflow definitions or runs in production. The nine retired rules in three staging test workflows were removed through revision-guarded builder mutations, preserving every supported action. Historical staging runs, transition receipts, and their schema fields remain readable as audit evidence; they grant no current movement authority. The internal goal review still uses an `evaluate_goal` run receipt, but it is generated by the completion engine, not configured by a builder.

## Authority and replay

Transition authority rechecks workflow revision, membership activity, activation sequence, current stage visit, and product evidence in the same write. Action and assessment receipts are bound to exact rules and source records. Replays cannot create another transition. Member-facing context excludes private builder prompts and assessment details. Server-side access checks govern both member and manager views.
